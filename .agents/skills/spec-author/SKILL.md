# Spec Authoring

Conventions for everything under `knowledge/product/specs/`. These exist so cycles can be reordered, renamed, and revised without rotting cross-references between them.

---

## 1. Folder and file format

Each cycle lives in its own folder directly under `knowledge/product/specs/`:

```
knowledge/product/specs/<seq>-<ID>-<slug>/
  <ID>.md       ← the spec — the folder's owning note, named by its stable ID (e.g. ZOD020.md). See §1.5.
  PLAN.md       ← generated by /tdd-cycle-generator
  RETRO.md      ← generated by /retrospect after completion
```

The owning note is named **`<ID>.md`** (e.g. `ZOD020.md`), **not** `SPEC.md`. This is deliberate: Obsidian resolves `[[<ID>]]` cross-references by **filename**, which is rock-solid — no dependency on the frontmatter `aliases` cache (which silently fails to index on bulk/external edits). The `aliases` (ID + human title) remain as a convenience so `[[<Human Title>]]` also resolves. For a **plan-only** cycle (no spec of its own), the owning note is the plan, likewise named `<ID>.md`.

The folder name follows the pattern:

```
<seq>-<ID>-<slug>
```

| Field    | Example   | Rule                                                         |
|----------|-----------|--------------------------------------------------------------|
| `<seq>`  | `004`     | 3-digit priority / implementation-order prefix. **May be renamed on reorder.** |
| `<ID>`   | `BUD019`  | Area code + stable identifier (the spawning GitHub issue's number — see below; older IDs are 3-digit, newer ones vary). **Never changes.** |
| `<slug>` | `sdk-adapters` | Short kebab-case description.                           |

**Seq is priority, not authorship date.** The seq prefix orders cycles by *when they will be implemented* (i.e., priority / chronology of build), not by *when the spec was written*. Pick a seq that places the new cycle adjacent to the work it follows. Two cycles can share a seq prefix if they ship in the same window — the filesystem just sorts them by ID/slug after the shared prefix. This is the recommended layout when several cycles implement the same spec (see §1.5). Renumber other folders only when the resulting drift is clearer than letting them stay.

**Area codes:**

| Code  | Area                                                                |
|-------|---------------------------------------------------------------------|
| `BUD` | retired — budd (agent runtime, adapters, transports), superseded by `ZOD`; existing IDs preserved as legacy references |
| `ZOD` | zooid — agent runtime, transports, runtimes, CLI                    |
| `ZNC` | Zoon Client — the matrix-js-sdk UI app                              |
| `ZCL` | Zoon Cloud — managed control plane (reconciler, evals, billing, hosted homeserver) |
| `MAT` | Matrix infrastructure — self-hosted homeserver setup, federation     |
| `ZON` | retired — split into `ZNC` (client) and `ZCL` (cloud); existing IDs preserved as superseded references |

**Assigning `<ID>`.** The number is the **GitHub issue number** of the issue that spawned the spec — not a locally-scanned "next free number." **Every area code mints from the same pool: `zooid-ai/zooid`'s issue numbers**, regardless of which repo the underlying code actually lives in. The prefix is a triage classification, not a repo pointer. This is deliberate: `open-issue` files anything that might be spec-worthy in `zooid-ai/zooid` in the first place, even when the affected code lives in `clients` or elsewhere — only small, scoped bugs/UI tweaks that clearly don't need a spec (per §5) stay in the repo that holds the code. One shared pool keeps the scheme collision-free with a single rule instead of a per-area repo table to keep straight.

Mint the ID when product triage decides the issue graduates to a spec (not at issue-creation time — most issues never need one): take the issue's number and prefix it with the area code, e.g. issue `zooid-ai/zooid#142` classified as a client concern becomes `ZNC142`.

**If the graduating issue isn't already in `zooid-ai/zooid`** — it was filed directly against `clients` or another code repo, which happens for issues that looked like a small scoped fix at filing time but turned out to need a spec — **transfer it to `zooid-ai/zooid` first**, then mint the ID from its new, post-transfer number. GitHub issue transfers always get a fresh number in the destination repo, never the original one; never mint from the pre-transfer number.

If a spec is authored without a preceding issue at all (rare — nearly all spec-worthy work starts with `open-issue`), open one directly in `zooid-ai/zooid` purely to mint the number. **Label it `self-triaged` when you open it** (`--label self-triaged`). Every new `zooid-ai/zooid` issue fires the triage webhook, which wakes the cloud product-owner; on an unlabeled spec-worthy issue it drafts its own spec at the same `<ID>` path within a minute, and you end up with two competing PRs for one spec (ZOD109: zooid-ai/product#52 and #53). The label is how product-owner's own `gh-issue-create.mjs` avoids triaging its own issues, and the webhook skips anything carrying it. Same rule when you file an issue that you, not product triage, will spec. If one spec consolidates two related issues (e.g. a duplicate), mint from whichever one triage was actually acting on and cross-link the other on GitHub — don't invent a rule for picking the "right" one.

Never mint from the spec's own PR number in `zooid-ai/product` — that's a different repo's number sequence entirely and has nothing to do with the ID.

GitHub issue numbers are unique per repo, so two specs can never independently claim the same ID — there's no scan-and-race step, so the old "`git pull` before assigning, keep earliest claimant, renumber the newcomer on collision" ritual is gone; it existed only because IDs used to be assigned by scanning `main`, and a spec's PR can sit unmerged for a long time awaiting architect review while another cycle scans the same (stale) `main` and picks the same number. Still `git push` promptly as normal practice — just not for collision-avoidance.

As a cheap sanity check before creating the folder: if `specs/*-<prefix><issue#>-*` already exists, **stop and investigate — don't just renumber past it.** With a single shared issue pool this should never legitimately fire; if it does, something upstream is wrong (most likely an untransferred issue whose number got reused, or a manual/legacy-numbering error), and papering over it with a renumber would hide that.

This scheme replaced sequential per-area numbering on 2026-09-28; `ZOD` specs already ran up to `ZOD094` while `zooid-ai/zooid`'s issue counter was still in the 40s, so issues #44–#94 in that repo were deliberately burned (created and deleted) to clear the range — the next `zooid-ai/zooid` issue that graduates to a `ZOD` spec lands at `095` or higher; a large jump from `094` is expected. `ZNC`/`ZCL`/`MAT` needed no such fix.

IDs are sparser than before — skipped numbers (every `zooid-ai/zooid` issue that never becomes a spec, now shared across all four areas) are expected and fine; never renumber.

**Cross-references** use `[[<ID>]]` wikilinks (e.g. `[[ZOD018]]`), which resolve to `<ID>.md` by filename — **never** the seq prefix or slug. Seq and slug can drift; the ID can't.

**Legacy epics** live under `epics-legacy/` and use the old categorical structure. When a legacy epic is referenced, use its folder path, not an ID.

## 1.5 Specs vs. cycles — one spec, possibly many cycles

A **spec** is a design artifact: the *what and why*. A **cycle** is a unit of work: it ends in a branch, a retro, and (usually) a PR. Most cycles introduce their own spec, but they don't have to — when implementation of one spec spans multiple cycles, **each cycle is its own cycle folder**.

**Two cycle shapes:**

1. **Spec-introducing cycle** — folder contains `<ID>.md` (the spec it owns) plus `PLAN.md` and `RETRO.md` for the first implementation cycle.
2. **Plan-only cycle** — folder contains `<ID>.md` (the plan, named by its own ID) and `RETRO.md` only. The plan carries `implements: "[[<spec-ID>]]"` in its frontmatter to point at the spec it executes against.

**Why split cycles into separate cycle folders rather than `PLAN-02.md`, `PLAN-03.md` in one folder:**

- Each cycle maps cleanly to one branch / one PR / one retro — no `RETRO-02.md` suffixes.
- Status of *implementation* is per-cycle; status of the *spec* is independent (the spec can be `shipped` while the next cycle is still `draft`).
- If a cycle is dropped or rescoped, only that cycle's folder is affected.
- Different people / time windows can pick up later cycles without touching the spec-owning folder.

**Conventions:**

- The spec-owning folder keeps its ID and slug forever, even after subsequent cycles ship in other folders. The slug should describe the spec, not just cycle 1 (e.g. `observability`, not `observability-floor`).
- Plan-only cycles pick the next free ID in their area. They are NOT given suffixed IDs (`ZOD036b` is wrong; `ZOD037` is right). The link to the spec is the `implements` frontmatter reference, not the ID itself.
- Plan-only cycle slugs should describe their *cycle's* scope, not the spec (e.g. `observability-bridge` for the second cycle of `[[ZOD036]]`).
- Place plan-only cycles at a seq that puts them next to (often sharing) their predecessor's seq prefix.
- The spec's `**Implementation cycles:**` block (see §2) lists every cycle folder that implements it, in implementation order. Add an entry when a new plan-only cycle is created.
- Cross-references stay ID-based: `[[ZOD036]]` resolves to whichever folder owns that spec; `[[ZOD037]]` resolves to its plan-only cycle.

## 2. Top-of-file metadata

### 2.1 The spec note (`<ID>.md`)

Every spec note (`<ID>.md`, e.g. `ZOD020.md`) opens with YAML frontmatter, then the H1 title, then a `## Changelog` section:

```md
---
id: <ID>                 # area code + stable number, e.g. ZOD024. Never changes.
type: spec
order: <seq>             # integer; mirrors the folder's <seq> prefix (priority/build order)
status: draft            # draft | approved | shipping | shipped | superseded | dropped
title: <Human Title>     # mirrors the H1 below; quote only if YAML needs it (see below)
aliases:                 # so [[<ID>]] and [[<Human Title>]] resolve to this spec in Obsidian
  - <ID>
  - "<Human Title>"
created: YYYY-MM-DD       # earliest changelog date
updated: YYYY-MM-DD       # most recent changelog date
# superseded_by: "[[ID]]" # required when status: superseded (quoted — a leading [ is a YAML flow sequence)
# dropped: "<reason>"    # required when status: dropped
# trigger: "<condition>" # optional: activation condition for a deferred spec
---

# <Human Title>

## Changelog
- YYYY-MM-DD: drafted
- YYYY-MM-DD: <what changed, short>
- YYYY-MM-DD: approved
```

The frontmatter is the **queryable surface** — Obsidian Properties / Dataview / Bases sort and filter on it, so keep `status`, `order`, `created`, `updated` accurate. The `aliases` (ID + human title) are what make `[[<ID>]]` cross-references resolve to this spec in Obsidian — keep the title alias in sync with the H1.

**Quoting: Obsidian wins.** Editing a note in the app rewrites its frontmatter — Obsidian strips quotes it considers unnecessary and keeps the ones YAML actually needs. Don't fight it, and never re-quote a value it has stripped: that is a round-trip the editor will just undo, and it turns a no-op into a diff.

Quote only where YAML would otherwise misread the value:

- **a leading `[`** — `implements: "[[ZOD072]]"`, `spec:`, `superseded_by:`. Unquoted, YAML reads a flow sequence. Obsidian keeps these quoted, correctly.
- **a colon followed by a space**, anywhere in the value.
- **a leading `#`, `&`, `*`, `!`, `%`, `@`, `` ` ``, `|`, `>`, `-`** or a quote character.
- **a string that would otherwise parse as another type** — `1.0`, `true`, `null`, `2026-01-01`.

Otherwise leave it bare. A `title:` containing an em-dash, parentheses, or a slash needs no quotes, and Obsidian will remove any you add. Both forms are valid YAML; neither is worth a diff.

- **Status** progresses through the active lifecycle: `draft` → `approved` → `shipping` → `shipped`. Update `status` on change.
  - `shipping` means *some* implementation cycle has merged. Stay in `shipping` until every cycle listed under **Implementation cycles** has shipped.
  - `shipped` means every listed cycle has shipped. Cycles added later can move it back to `shipping`.
- **Terminal statuses** that don't represent shipped work:
  - `superseded` — the spec is replaced by another that carries its concerns forward. Add `superseded_by: "[[ID]]"` to the frontmatter.
  - `dropped` — the spec is abandoned and not replaced (premise invalidated, scope deemed unnecessary, etc.). Add `dropped: "<one-line reason>"` to the frontmatter.
- A spec that was partially shipped before being superseded should still be marked `superseded` — what matters is whether the spec's *intent* is now carried by something else.
- **`created` / `updated`** are derived from the changelog: `created` = earliest entry date, `updated` = latest. Bump `updated` every time you add a changelog entry.
- **Changelog** lives in the `## Changelog` body section, chronological, one bullet per material revision. Typo fixes don't earn a bullet; design changes and status transitions do.

When a spec is implemented across more than one cycle, add an **Implementation cycles** block immediately under the Changelog:

```md
**Implementation cycles:**

- **[[ZOD036]] — capture floor.** §1, §2, §4, §5, minimal §6. Status: shipped.
- **[[ZOD037]] — bridge & polish.** §3, §6 (rest), §7, §8. Status: draft.
```

Each entry is one line: cycle ID, short cycle name, scope summary, current status. Update when a cycle is added or its status changes. The list is the canonical record of how the spec is being delivered — anyone reading the spec should know from this block alone where each piece lives.

### 2.2 PLAN.md and RETRO.md

Every plan and retro note opens with light frontmatter so Obsidian can join the spec, plan, and retro that share a cycle folder. (A spec-introducing cycle's plan/retro are `PLAN.md`/`RETRO.md`; a plan-only cycle's plan is its `<ID>.md` owning note, with a sibling `RETRO.md`.)

```md
---
id: <ID>                       # the folder's own ID (the <ID> segment of the folder name)
type: plan                     # or: retro
order: <seq>                   # mirrors the folder's <seq> prefix
title: "<H1>"                  # mirrors the H1 below
implements: "[[<spec-ID>]]"    # PLANs: the spec this cycle implements (backlinks to it)
# spec: "[[<spec-ID>]]"        # RETROs use this field name instead of `implements`
# status: draft                # plan-only PLANs: this cycle's status (draft | shipping | shipped)
# aliases: [<ID>, "<H1>"]      # plan-only PLANs only: they own their ID, so [[<ID>]] resolves here
---

# <Cycle title>
```

- `id` is the implementing cycle's **own** ID (a plan-only cycle `ZOD037`'s `id` is `ZOD037`), never the spec it implements — that link is `implements`/`spec`.
- `type` discriminates the note kinds in a folder; together with `id` and `order` it lets Dataview/Bases group spec + plan + retro per cycle.
- **Every PLAN** carries `implements: "[[<spec-ID>]]"`, **every RETRO** carries `spec: "[[<spec-ID>]]"` — the backlink to the spec the cycle targets. For a spec-introducing plan/retro that's the same-folder spec (its own ID); for a plan-only one it's the cross-folder spec it executes. This is what connects plans and retros to their spec in the graph.
- **Plan-only PLANs** (the `<ID>.md` owning note) additionally carry `status` (cycle status, independent of the spec) and `aliases: [<ID>, "<title>"]`. Since the file is `<ID>.md`, `[[<ID>]]` resolves to the plan by filename; the aliases just add `[[<title>]]`. A `**Spec:** [[<spec-ID>]]` line in the body links the spec in-text; the `implements` field is canonical.
- Spec-introducing plans/retros and all bodies (Goal/Scope, Branch/Result, etc.) are otherwise unchanged.

## 3. Standard sections

Use these headings in order. Skip ones that don't apply — an empty section is worse than no section.

1. **Context** — why this spec exists; what's broken or missing today.
2. **Concept** — the core idea, names, and relationships being introduced. Prose, not code.
3. **Design** — key technical decisions, interfaces, config shapes, data flows.
4. **Package structure** — which packages change or are created.
5. **Relationship to other specs** — dependencies and interactions. Reference by ID.
6. **Non-goals** — explicit scope exclusions. Make them precise.

## 4. Cross-reference rules

- Reference other specs using wikilink notation: `[[BUD018]]`, `[[ZON012]]`.
- **Do not** reference by folder name (`knowledge/product/specs/004-BUD019-sdk-adapters`) — paths change.
- **Do not** reference by seq number (`[cycle 4]`) — seq is unstable.
- When a spec is superseded, set Status to `superseded` and add `**Superseded by:** [ID]` under the Status line. When a spec is dropped without replacement, set Status to `dropped` and add `**Dropped:** <reason>` under the Status line.

## 5. When to start a new spec, a new cycle, or edit existing

**First: does it need a spec at all?** Not every change does. A spec earns its
place only when the work (a) spans **more than one package**, (b) requires a
**migration**, or (c) introduces a **genuinely new concept** — not a mere
improvement or addition to an existing feature. Small, self-contained features,
UX tweaks, copy changes, and bug fixes are tracked as **GitHub issues** and go
straight to a PR — no spec, no cycle. Over-speccing (a five-section spec for a
tooltip) is as real a failure as under-designing. Link such issues to the spec
whose feature they touch (the board's `Spec` field) without editing that spec.

Once a spec *is* warranted, three actions for three situations:

- **Edit the spec** when the change refines the same proposal: reshape a config schema, tighten a non-goal, clarify an interface.
- **New plan-only cycle** when implementation of an existing spec is split across cycles, or when a later cycle is picked up after the first has shipped. The spec stays put; a new folder under `knowledge/product/specs/` carries its own PLAN.md with `implements: "[[<spec-ID>]]"`. Update the spec's **Implementation cycles** block.
- **New spec (in its own cycle folder)** when the change introduces a new concept with its own lifecycle, even if it touches the same packages.

When the boundary is unclear:

- "Same intent, different cycle" → plan-only cycle.
- "Different intent, related work" → new spec.
- Adding an ID is cheap, whether for a plan-only cycle or a new spec; splitting a giant spec or a giant cycle later is expensive.

## 6. Specs vs. plans vs. retros

**Specs (`<ID>.md`):** architecture, design decisions, interfaces, config shapes, data flows. Answer *what and why*. No step-by-step instructions, no full code blocks. One spec lives in one folder for the lifetime of the project.

**Plans (PLAN.md):** fully detailed, dev-ready TDD cycle — exact file paths, complete test code, runnable commands, phase-by-phase instructions. Generated from specs via `/tdd-cycle-generator`. Each plan lives in its own cycle folder (the spec-introducing folder for cycle 1; a plan-only folder for each subsequent cycle).

**Retros (RETRO.md):** what was done, what deviated from the plan, lessons learned. Generated via `/retrospect` after completion. Lives in the same cycle folder as its plan — never with a numeric suffix, since each cycle has its own folder.
