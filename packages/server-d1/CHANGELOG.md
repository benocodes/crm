# @vibase/server-d1

## 0.4.0

### Minor Changes

- 4690105: Accepting an agent invitation links the new sign-in account to the agent it names: the account becomes that agent (same id, name and scopes, its API keys keep working), and no invitation creates an agent any more. An agent that is disabled, delegated, unknown or already linked refuses the sign-up and leaves the invitation pending.
- 8396747: An agent invitation names an existing agent: `vibase invitations create --agent-id <id> --email <agent-email>` (the role is implied; `--role agent` without `--agent-id` is refused with `agent_id_required`). The agent must exist and may not be a form agent, a delegated agent, a disabled agent or one that already has an account. Creating another invitation for the same agent revokes its live ones, and the invitation records carry `agent_id`. After `vibase agents create`, the CLI prints both routes to a credential (`api-keys create --agent-id`, `invitations create --agent-id`) on stderr, and the owner-login warning names them too. The control database's genesis gains `invitations.agent_id`, so an instance must be reinstalled from this build.

### Patch Changes

- a6c1380: An agent account that claims its invitation now sees "Your agent account is ready" with how to sign in (`vibase login`, MCP or the SDK) instead of "No access to this workspace". The CLI's owner-login warning names both routes for an agent identity: an invitation for an agent that can use a browser, and `agents create` with `api-keys create` for a headless one.
- 9f344b1: The ready card for a claimed agent account says the account is the agent itself and acts with the permissions an owner granted it. A refused invitation acceptance (the invite page, the sign-in page and the auth server's message) no longer promises that signing in will finish setup: it says to try again and then ask the person who invited you to check the invitation.
- c831b8a: The agent's "Your agent account is ready" card gives the `vibase login --server <this instance>` command with a Copy button, and says what to do when the CLI is already signed in.

## 0.3.0

### Minor Changes

- ca8755e: An approval request now says what it asks for in the vault's own words. Every action request carries a `target_summary` (one line written when the request is created: the operation, the target record's name and the changed fields; for a send, the mailbox and recipients, with outside text quoted, stripped of hidden characters and shortened), and reads show who proposed it (`proposer_kind`, `proposer_name`, `proposer_acting_for` for a delegated agent) and, for a send, the `sending_mailbox`. The reference approvals app leads each card with them and shows the proposer's own reason below, labelled, clamped and without bidi controls. Migration `0030_action_request_target_summary` adds a nullable `action_requests.target_summary`; run `vibase-server upgrade` to apply it. Requests created before the upgrade have no summary and the app shows the operation name.
- fcc47b2: `CORS_ALLOWED_ORIGINS` and `AUTH_TRUSTED_ORIGINS` now accept a wildcard origin, `https://*.<host>[:port]` (`http://*.localhost:5173` too, where the variable allows `http`). It matches subdomains of `<host>` at any depth, never the bare host, another scheme or another port, and is the same pattern Better Auth uses for its own trusted origins. A matched origin is answered with its own `Origin` and `Vary: Origin`. Exact entries answer as before. There is no public-suffix guard: `https://*.workers.dev` trusts every Cloudflare customer, and a wildcard in `AUTH_TRUSTED_ORIGINS` gives every matched origin on the API's own site the session on `/auth`. `CLERK_AUTHORIZED_PARTIES` still refuses wildcards. The session cookie is unchanged.
- b7a771f: A bearer app's origin in `CORS_ALLOWED_ORIGINS` (exact or a wildcard) can now call `/auth/oauth2/register` and `/auth/oauth2/token` with `fetch` and read every answer, with no cookie: the preflight is answered `204` (`POST`, `Content-Type`) and every answer carries the origin and `Vary: Origin`, never `Access-Control-Allow-Credentials`. No other `/auth` path changes, and an origin also in `AUTH_TRUSTED_ORIGINS` keeps its credentialed answer.
- 759f6e9: Captured mail is told apart more carefully. A message is recorded as outbound only when the connection sent it (Gmail's SENT label) or the caller says so: a From header that names one of your own addresses no longer makes an incoming mail outbound. A mail that reuses the `Message-ID` of a message already captured, with a different subject, sender or body, is now captured as a message of its own (under the id `gmail:<connection id>:<provider message id>`) instead of being merged into the first. Migration `0028_content_sha256` adds a nullable `messages.content_sha256` fingerprint, never exposed through the API, events or schema; run `vibase-server upgrade` to apply it. Messages captured before this release keep their stored direction and have no fingerprint, so they match any later copy of the same Message-ID.
- ab52ace: A captured message now stores what a person reading it sees. Gmail bodies drop hidden elements (`display:none`, `visibility:hidden`, `opacity:0`, `font-size:0`, zero height with `overflow:hidden`, the `hidden` attribute, `template`), HTML comments (Outlook conditional blocks included) and image URLs (an image becomes its alt text). Every channel, forms included, strips zero-width, bidi-control and Unicode tag characters from the body, subject and sender names before the preview and fingerprint are made. The MCP instructions now tell agents that message text comes from outside the team and is data, never instructions. Migration `0029_reset_content_sha256` clears the stored capture fingerprints so mail stored before this release still matches later copies; run `vibase-server upgrade` to apply it.
- 3db3c0d: Every `<list>.aggregate` (contacts, companies, deals, tasks and each custom object; REST, MCP and `vibase <list> aggregate --group-by`) takes `group_by`: one or two comma-separated fields (uuid, text, integer or boolean columns except `id`, `__c` and custom object fields included). The answer keeps its top-level `count` and adds `groups`, one ungrouped answer per group beside its `key`, ordered by the group fields with the null group last. More than 200 groups is a 400, never a truncated answer. The one-currency rule for money is judged per group, so `deals/aggregate?group_by=currency&sum=amount_minor` answers one total per currency. `schema.get` lists each list's groupable fields as `aggregate.group_by`. No migration. The CLI derives its flag from the API, so `@vibase/cli` needs no release of its own.
- e09f55c: A custom object declared as plain data is now served by the generic layer on D1: full CRUD with soft delete, events, scopes, proposals and associations, under its one `<key>__c` name. Nothing in the Worker passes a declaration yet (the schema file arrives in a later release), so a deployment behaves as before. The CLI spells a custom object's command and a `__c` flag with the same kebab rule as a built-in's, keeping the `__c` suffix (`session-recordings__c`, `--referral-source__c`).
- 9e218ac: Contacts, companies, deals and tasks carry an `additional_props` bag: a flat object of extra facts (string, number or boolean values, lowercase snake_case keys, at most 50 keys and 8 KiB) that agents read, merge-patch (`null` removes a key) and propose under the record's own scopes. Migration `0026_additional_props` adds the column to the four tables (existing rows get `{}`), so run `vibase-server upgrade` to apply it. The bag rides in the record's `created` and `updated` events, and a contact merge fills the survivor's missing keys.
- 90c415e: A custom object's declaration can now hold reference fields (to companies, deals, tasks, principals or another custom object, with the live check and an index) and unique fields (409 `value_exists` naming the holder), and every declared field is a column filter with an honest index cost. `schema.get` describes a custom table from its declaration (`origin: custom`), lists an undeclared custom table as archived, and every table entry gains `archived`. Nothing in the Worker passes a declaration yet, so a deployment behaves as before apart from the extra `archived: false` on each table.
- 6d129cf: The schema file (`version` 1, `define` keyed by `<key>__c`) is validated with named errors, and its JSON Schema, `vibase.schema.schema.json`, ships beside the Worker in the server package. A new apply makes a D1 database's `__c` tables match the file: it creates missing tables and indexes, adds new fields, archives what the file no longer declares (nothing is dropped), and refuses kind, target, required and default changes, a removed `unique`, and data a new unique index would violate, before any change is made. Nothing in `redeploy` reads a file yet, so a deployment behaves as before.
- bb6114f: `vibase-server redeploy --schema <path>` attaches a schema file of custom objects. It validates the file, applies its `__c` tables to the database after the core migrations, uploads the Worker with the file as a `vibase.schema.json` Text module, records the file's path in the settings so a later `redeploy` or `upgrade` attaches it again, and waits for `/health` to show the file's digest. A refused plan (a changed kind or target, a unique field that live rows violate) changes nothing, and a run with no file is refused while the live Worker carries one. The Worker serves the custom objects from start, lists their scopes in its early discovery answers, shows them as one "Custom records" area on the consent page, reports the file's digest and object names in `/health` and `vibase-server status`, and answers every route but `/health` with `503 schema_invalid` when it cannot load its file.
- 58d43a5: Every custom object now carries the `additional_props` bag too (a new `__c` table gets the column, and `vibase-server redeploy` adds it to an existing one, once). Lists of contacts, companies, deals, tasks and custom objects, and `deals aggregate`, take `additional_props=<key>.<condition>` (`eq`, `neq`, `in`, `is.null`, `not.is.null`; a string matches by its text, a number or boolean by its JSON literal; no index serves it). A new read, `<resource>.property_keys` (`GET /api/v1/<resource>/property-keys`, MCP `<resource>_property_keys`, CLI `<resource> property-keys`), lists the bag keys in use with record counts and JSON types, never a value. `schema.get` describes the bag column's rules.
- e7b1782: `contacts.merge` fills the survivor's custom (`__c`) fields from the source after tombstoning it, so a unique value the source held can move, and answers the survivor's record plus `merge_conflicts` (`[{ field, source_value }]` for every field where both contacts held different values; `[]` when none). A custom object's field, or an extension field on companies, deals and tasks, may reference `contacts` (`target: "contacts"`), and merge re-points those references to the survivor. An extension field on contacts cannot reference contacts (`reference_contacts_self`). The merge response schema gains `merge_conflicts`; no migration.
- 24f01bf: A deployment adds its own `<name>__c` fields to contacts, companies, deals and tasks by writing an `extend` section in its schema file. `vibase-server redeploy --schema <path>` validates it, plans the new columns and indexes with the custom objects, applies them after the core migrations and attaches the file; the Worker serves the fields on create, update, get, list filters, MCP and OpenAPI from start. `/health.schema` adds `fields` when the file extends, and a file that only extends counts as a file for the redeploy guard, `verify` and `status`. A file without `extend` behaves as before.
- 0ebd20a: The file that declares custom objects and extension fields is the schema file. `vibase-server redeploy --schema <path>` attaches it and records its absolute path under the `schema` key of the instance settings; `vibase.schema.json` is its conventional name, and its JSON Schema ships beside the Worker as `worker/vibase.schema.schema.json`. In the file, `define` declares new custom objects (required: an extend-only file writes `"define": {}`) and `extend` adds fields to contacts, companies, deals and tasks. `/health.schema` reports what is attached, `vibase-server status` and the redeploy plan print a `schema:` line, and a Worker that cannot load its file answers every route but `/health` with `503 schema_invalid`. The empty file that drops everything on purpose is `{"version":1,"define":{}}`.
- 521bdcb: On a Better Auth instance, connecting a Gmail mailbox now completes only in a browser signed in as the person who started it. The connect callback refuses a browser with no session, another member's session or a signed-out session with `session_mismatch` (403, or the return redirect), before it contacts Google and with nothing written, so a forwarded authorize link can no longer connect someone else's mailbox under the sender. On Clerk and no-provider instances the callback stays bound by its signed state alone. A person who sees this error signs in to the workspace in that browser and starts the connection again.
- 8985c4d: A list filter can now carry more than one condition on a field, so a list answers ranges. Repeat the query parameter (`GET /api/v1/deals?expected_close_date=gte.2026-11-01&expected_close_date=lt.2026-12-01`), or send an array to an MCP tool (`{ "expected_close_date": ["gte.2026-11-01", "lt.2026-12-01"] }`); the conditions on a field, at most 4, are ANDed with each other and with every other filter, on every list, custom object list, `action_executions` and `deals.aggregate`. Only column filters repeat: any other repeated parameter is still `400 validation_error`. In the OpenAPI document each column filter parameter is now a string or an array of 1 to 4 strings, and carries `x-vibase-filter` with its `kind` and `operators`. The CLI keeps one string flag per filter for now.
- 5ffe344: A column filter flag can be repeated to send a range: `vibase deals list --expected-close-date gte.2026-11-01 --expected-close-date lt.2026-12-01` sends two conditions, which AND together (up to 4 per field; the server refuses a fifth). `--help` marks the flags that may repeat. The filter parameter descriptions in the OpenAPI documents, the MCP tools and `schema.get` no longer say "once per field": they say the parameter may repeat and give a range example for text, integer and timestamp fields.
- 2f5f3a9: Contacts, companies, tasks and every custom object now answer `<name>.aggregate` (REST `GET /api/v1/<name>/aggregate`, MCP `<name>_aggregate`, CLI `vibase <name> aggregate`) with the list's own filters: a count, and the sum, average, minimum or maximum of fields by kind. A function with no field on a list (`sum` and `avg` on contacts, companies and tasks until an integer `__c` field is declared) is not a parameter of it, and naming it is a 400. `schema.get` reports each list's aggregate. **Six field names are now reserved for custom objects: `count`, `sum`, `avg`, `min`, `max` and `group_by`.** A deployed schema file that declares a custom object field with one of these names is invalid under this release and the Worker fails closed on it (503 `schema_invalid`) after upgrade until the field is renamed; `redeploy --schema` refuses such a file with `reserved_name` before any deploy step.
- ed232ef: Owners can register, list, read and delete first-party OAuth clients on the meta API (`POST/GET /meta/v1/oauth-clients`, `GET/DELETE /meta/v1/oauth-clients/{client_id}`, also MCP tools and `vibase` CLI commands from the meta document), with the new owner-only scopes `oauth_clients:read` and `oauth_clients:write` (never granted to agents or dynamically registered clients). A client is public (PKCE, no secret), skips the consent screen and signs people in to your own web app as themselves; `skip_consent: false` is refused for now. Deleting a client is the revocation: its refresh tokens stop working at once and access tokens already issued last at most one more hour. Needs `AUTH_PROVIDER=better-auth`; other deployments answer `501 provider_not_configured`.
- 5aff6b5: Owners can edit a first-party OAuth client (`PATCH /meta/v1/oauth-clients/{client_id}`, also an MCP tool): name, redirect URIs, scopes and `skip_consent` (the lists replace the stored ones; `skip_consent: false` is still refused). An edit revokes no token. Creating or editing a client now answers `warnings`: one entry for each redirect origin that is not in `CORS_ALLOWED_ORIGINS`, which means the app's browser calls to the token endpoint and the API are refused until it is added; the write happens either way. A client's redirect list also decides its stored type, so switching between an https and a loopback `http` redirect keeps sign-in working.
- ce4007d: A person who signs in through a first-party OAuth app (one an owner registers with `oauth_clients.create`) now acts as themselves: `me.get` names the user, writes are attributed to them, and no delegated agent is created for the app. Their scopes are their own role met with the app's scopes, read on every request: the token's own scope list no longer narrows them, and an app that was given no list (the new default: `scopes` omitted on create answers `scopes: null`, and `oauth_clients.update` accepts `scopes: null`) holds every scope a first-party app may hold, including ones you declare later, never an administrative scope. An edit to an app's scopes, or deleting the app, now reaches tokens already issued within about a minute; a token whose app no longer exists is refused (this applies to dynamically registered clients too). Apps registered before this release keep the list they were created with; set `scopes: null` on one to have it follow new scopes. Delegated agents that earlier first-party sign-ins created are left as they are. No migration.
- 9991cf3: A person's default `vibase login` on the built-in provider now asks for the wildcard `all_permissions` (named in discovery as `auth.full_access_scope`) instead of a snapshot of every scope, so the person holds their live role, including permissions declared after they signed in, on the same token (their role is read on every request, so a demotion applies at once). A login made before this version keeps its list, so run `vibase login` once to get full access. A `--scope` login stays limited to its list, `--scope all_permissions` is refused, an agent account that approves the wildcard gets its record at that moment and never the wildcard, a connector cannot ask for it, and the device page states full access in words. `agents.create` and `agents.update` now accept any custom scope the registry declares, whatever scopes the caller's own sign-in lists.
- cb730d6: A connector that registered itself before a scope existed (for example before a custom object was declared with `redeploy --schema`) can now authorise again with the same client: at `/oauth2/authorize` the stored scope list of a dynamically registered client is grown to include every scope a new registration may ask for, never removing one and never adding the wildcard or a human-only scope. The connector reaches the consent page asking for the new scope and keeps the same delegated agent; the new scope still needs the owner's grant on that agent's record. Clients created by an owner, first-party apps, disabled clients and the CLI client are left as they are.
- 0b344a0: An agent account's sign-in now holds only what its record grants at that moment: when it approves a login (the device page, or a connector's consent page) the requested scopes are narrowed to its record, so a scope granted later needs `vibase login` as the agent again (same agent id; removals still apply at once). To say so, a `403 insufficient_scope` for a scope the caller's role or record holds but its sign-in lacks now ends with how to fix it (`vibase login`, or reconnect the connector), MCP lists such a tool with that hint, `agents.update` answers with a `sign_in_notice` when it adds scopes to an agent that signs in, and the CLI prints that notice and tells an agent with no scopes to sign in again once granted.
- 338b98d: A connector's stored scopes now follow its sign-in. A delegated agent (an MCP client signed in by a person) used to be created holding every agent-grantable scope whatever the person approved; its record is now the scopes of its latest sign-in (the token's list, closed, met with the person's role), on the built-in provider and on Clerk. A sign-in that lists something different rewrites the record with one `agent.updated` attributed to the person; a refresh or a sign-in with the same list changes nothing, so a scope an owner removed with `agents.update` stays removed until the connector signs in with a different list. A delegated agent refused a scope it was not approved for now gets the plain `403 insufficient_scope`, and MCP no longer lists a hinted tool for it. Migration `0031_connector_consented_scopes` adds a nullable `agents.consented_scopes` (never shown in any answer); run `vibase-server upgrade` to apply it. A connector created before the upgrade is corrected by its next request.
- b6aad39: `agents update` on a connector (a delegated agent) can now narrow its scopes only within what the person approved when it signed in: a scope outside the consent answers `409 scope_not_consented` and writes nothing. Any change to a connector's scope list, an add back or a removal, now answers one `sign_in_notice` saying a later sign-in with a different list replaces it and pointing to an agent account for a hard limit. The agents guide and the Clerk page say so.
- 4c8fc4c: A person can approve for a connector only what their role holds. On the built-in sign-in the consent page shows the permissions the signed-in account cannot approve as off and disabled ("Your role in this workspace doesn't include this" for a person, "This agent account hasn't been granted this" for an agent account), and the server cuts an accepted consent to the requested permissions the account holds, so a hand-made request naming more is narrowed, not refused. If the page cannot load what the account may approve it offers Deny only. A raised role reaches a connector through its next consent. The page reads the list from a new same-origin `GET /auth/consent-bound` (session cookie, `401` without one). The CLI device login and Clerk are unchanged.
- 91c8125: The database migrations are squashed into one genesis file per database: `migrations/0001_genesis.sql` for the CRM database and `control-migrations/0001_genesis.sql` for the control database. They build the same schema the 31 CRM files and 5 control files did, so a new install is unchanged. An install made before this version cannot upgrade, because its `d1_migrations` holds the old file names and genesis would run `CREATE TABLE` over existing tables and fail without changing anything. Reinstall it instead: destroy the instance's databases and set it up again.
- 371360d: A task's free text is now `description` instead of `notes`, on every surface: the `tasks` table and its full-text index, the REST, MCP and CLI task commands and filters, `tasks aggregate --group-by`, the schema document, task events and webhook payloads. There is no `notes` alias: sending `notes` on a task is refused like any other unknown field. The notes resource is unchanged. There is no upgrade path: the change edits the genesis migration in place, so an existing instance is reinstalled, as for the genesis squash.
- cef402f: The connection tables carry channel-neutral names: `channel_connections` is `connections`, `channel_credentials` is `connection_credentials`, `mail_sync_cursors` is `connection_sync_cursors` (its `history_id` column is `cursor`), `mail_sync_state` is `connection_sync_state` and `gmail_watches` is `connection_watches` (its `mailbox` column is `address`), with their constraints and indexes renamed to match. The schema document (`schema_get`) names `connections` as the foreign-key target wherever it named `channel_connections`. There is no upgrade path: the change edits the genesis migration in place, so an existing instance is reinstalled, as for the genesis squash.
- 860e67d: The Gmail sync Workflow is `GmailSyncWorkflow` on the `GMAIL_SYNC` binding (it was `MailSyncWorkflow` on `MAIL_SYNC`), its instance ids start `gmail-sync-`, and a new instance's Workflow is named `vb-gmail-sync-<env>`, so the longest accepted `--env` for `vibase-server setup` is 49 characters. An instance that records a Workflow name keeps it. A deployment config that binds `MAIL_SYNC` must bind `GMAIL_SYNC` with class `GmailSyncWorkflow`; there is no alias for the old binding or class, and the team's `smoked1` and `hq` are reinstalled rather than upgraded.
- 7f56ed3: A custom object's name now follows each surface's case convention and keeps its `__c` suffix: a multi-word object `session_recordings__c` is served at `/api/v1/session-recordings__c` (its `schema.get` `path` says so), its CLI command is `vibase session-recordings__c <action>`, and a flag for a multi-word `__c` field is `--referral-source__c` (the request still carries `referral_source__c`). The old spellings are gone, with no alias: `/api/v1/session_recordings__c` is a 404 and `--referral_source__c` an unknown flag. Stored names, schema file keys, operation ids, MCP tool names, scopes, event types and every JSON or query field name keep the snake_case `__c` name; one-word objects such as `projects__c` and every built-in are unchanged. The generated SDK map (`@vibase/sdk`) names the namespace `sessionRecordings__c`. No migration.
- 3dff955: The served OpenAPI document now carries `x-vibase-aggregate` on every `<list>.aggregate` operation: the fields each function (`sum`, `avg`, `min`, `max`) and `group_by` take, and the money fields with their currency columns, the same object `schema.get` publishes as `resource.aggregate`. The TypeScript SDK reads it to type `vibase.<list>.aggregate(...)`. Parameters, REST, MCP tools and the CLI are unchanged.
- 20d6178: A form's visitor check is now its own setting. `forms.challenge` is `none` or `turnstile`: a new form defaults to `none` (open, still behind the honeypot, origin allow-list, blocklist and rate limits), `turnstile` requires a passed Cloudflare Turnstile token as before. Migration `0027_form_challenge` adds the column and gives every existing form `turnstile`, so no form's behaviour changes; run `vibase-server upgrade` to apply it. Set it with `forms.create` / `forms.update` (`challenge`).

### Patch Changes

- c031246: An `extend` field on contacts, companies, deals or tasks can no longer be both `unique` and have a `default`: `setup` and `redeploy` refuse the schema file with `unique_with_default`, naming the field, because every row the vault creates itself would take the default and a second one would collide on the unique index. Custom objects are unchanged, and `unique` with `required` and no default is still accepted.
- 75a8625: a custom object can no longer have a field named `or`, `and`, `not` or `select`: the names are reserved for later filter grouping and column-selection parameters. A schema file that already uses one fails after upgrade: the Worker answers `503 schema_invalid` until the field is renamed, and `redeploy --schema` refuses the file with `reserved_name` before any deploy step. Object names, `__c` fields on built-in objects and property bag keys are unaffected. No migration.
- 6df8b44: One malformed or deeply nested email can no longer stop a mailbox's capture. Deep HTML is parsed under a depth bound that keeps its text, MIME parts nested past 32 multipart levels are ignored, and a message that still cannot be mapped is skipped as `unreadable` (counted, with one warning log line carrying only its ids and the error name) so the page and its cursor move on.
- d479c85: A mailbox's identity can no longer be broken or re-owned by a write that only needs `contacts:write`. Deleting an identity, or changing its `contact_id` or `own`, is refused with `409 identity_in_use` while a connected mailbox uses it (disconnect the mailbox first). Marking an address as one of your own (`own: true`), or giving an own address a contact, now needs a signed-in person: an agent gets `403 user_required`. An API key is no longer issued for a delegated agent (`409 delegated_agent`: it acts through its member's OAuth grant), and keys already issued for one stop working, with the answer a revoked key gets. Deleting a record, and merging contacts, no longer stop at 100 linked rows: each cascade handles up to 4,000 rows per kind of dependant in one request (past that, `400 set_limit_exceeded` as before).
- cf34042: Only an owner can create, read, update, delete or rotate OAuth clients through the sign-in server's client endpoints, and a registration that carries a member's session is refused (an unauthenticated registration works as before). The hourly repair sweep also deletes device codes past their expiry and dynamically registered clients that were never used (no token or consent, no owner, older than 7 days), at most 500 of each per run. Google's signing keys are cached for 5 minutes per Worker and shared by Gmail push and the connect callback, with at most one fetch a minute; a push answers 503 while Google's keys are unavailable.
- 4a65cad: A list filter named like an `Object.prototype` member (`constructor`, `toString`) is an ordinary unknown filter (400, not 500). Google sign-in no longer sends `include_granted_scopes`. A reply to a message whose subject holds control characters is sent with them replaced by spaces.
- 33f010a: The CRM database's schema follows one set of conventions, held by a test: one id CHECK or a foreign key on every id column, one timestamp CHECK, every CHECK named, the unique (organization_id, id) index written one way and named `idx_<table>_organization_id_id`. No column's type, nullability, default or foreign key changes. There is no upgrade path: the change edits the genesis migration in place, so an existing instance is reinstalled, as for the genesis squash.
- db73bef: The control database follows the same schema conventions as the CRM database (canonical id and timestamp CHECKs everywhere, every CHECK named, `idx_<table>_<what>` index names, the unique (organization_id, id) index on webhook subscriptions), the declared text limits of contacts, companies and tasks are now database CHECKs (`contacts.name`, `companies.name`, `companies.domain`, `tasks.title`, `tasks.description`), and the tables and columns a schema file creates carry named CHECKs and a unique (organization_id, id) index. Capture, forms and contact merge already stay within the limits. No column's type, nullability, default or foreign key changes. There is no upgrade path: the change edits both genesis migrations in place, so an existing instance is reinstalled, as for the genesis squash.
- 31a6a40: The database schema is now frozen at this release: both `0001_genesis.sql` files (CRM and control) never change again, and every later schema change ships as a new numbered migration. Installs from this version upgrade forward with `vibase-server upgrade`. Installs from before it (a `0.2.x` build or any earlier `main`) have a different genesis and are reinstalled.

## 0.2.0

### Minor Changes

- f523d42: The API key operations (`api_keys.create`, `revoke`, `list`, `get`) now run on the control-plane database: a create or revoke writes its `control_audit` row and no `api_key.*` event, and keys held only in the CRM database by an earlier version are not listed, read or revocable through them (none are in use; they still authenticate until the CRM key table is retired).
- 9893b0d: Three machine endpoints move to a stable shape, and the old paths are removed (no alias, no redirect): the Gmail connect callback `GET /oauth/google/callback` is now `GET /oauth/callback/google`, Gmail push `POST /gmail/push` is now `POST /inbound/gmail`, and Clerk's webhook `POST /webhooks/clerk` is now `POST /inbound/clerk`. Google sign-in's `/auth/callback/google` is unchanged. After upgrading, an operator updates three console settings: the Gmail OAuth client's authorised redirect URI to `https://<api-host>/oauth/callback/google`; the Pub/Sub push subscription's endpoint **and** token audience to `https://<api-host>/inbound/gmail` (a token minted for the old audience is refused `401`); and, where a Clerk webhook is set, its endpoint to `https://<api-host>/inbound/clerk`.
- 30cecc8: `messages:read_metadata` is a grantable scope: an agent or an OAuth client holding it reads message and thread subjects (the list and get operations, the thread links, the event feed and webhook deliveries) without message text or attachments, which still need `messages:read`. Holding `messages:read` implies it, so every existing grant behaves as before; the agents page shows it as "read metadata". A caller with neither scope is refused with `requires messages:read_metadata`.
- 40213d3: The workspace app at `/home`, `/accounts` and `/agents` is now a single-page app: moving between its pages no longer reloads the browser, and the sign-in session and workspace are read once per visit. Deep links and refresh work as before, and the window title and the current sidebar entry follow the page.
- dbe708b: The five auth pages move under `/app`: `/sign-in`, `/invite`, `/reset-password`, `/consent` and `/device` are now `/app/sign-in`, `/app/invite`, `/app/reset-password`, `/app/consent` and `/app/device`, and the old paths answer `404` (no alias, no redirect). Every link the vault builds names the new path: the invitation and password-reset links (`<base>/app/invite#token=...`, `<base>/app/reset-password#token=...`), Better Auth's login and consent pages, the `verification_uri` the CLI prints, Google sign-in's error return, and the approvals app's sign-in link. The Worker's `run_worker_first` is now exactly `/`, `/app`, `/app/*` and `/assets/*`: `wrangler.jsonc` and the release fixture carry the four entries, so an instance upgrades with `vibase-server upgrade`. After upgrading, an operator updates any bookmark, Clerk or provider setting and `CONNECT_RETURN_URL`-style return setting that names an old auth path, and redeploys the approvals app so its signed-out link goes to `<api>/app/sign-in`. Invitation and reset links already sent still name the old paths and stop working: issue new ones.
- a39dd68: Migration `0021_capture_settings.sql`: every connection stores its capture settings. `channel_connections` gains `exclude_group_addresses`, `exclude_personal_domains` and `contact_creation`; new tables `connection_capture_labels` (INBOX and SENT for every existing connection), `connection_blocked_senders` and `blocked_senders` (the workspace blocklist, not yet writable). The connection record (`connections.get`, `connections.list`, `connection.created`) now carries `capture_labels`, `blocked_senders` and the three scalars. Defaults change nothing: capture and contact creation behave as before.
- 0f29f3c: `connections.update` (`PATCH /meta/v1/connections/{id}`, MCP tool `connections_update`, CLI `vibase connections update <id>`): the owner of a connection, signed in, changes its capture settings (labels, blocked senders, group-address and personal-domain exclusion, contact creation) in one call. A list replaces the whole list; every accepted call emits one `connection.updated`. The `connections:write` scope now reads "Connect and disconnect mailboxes, and change their capture settings".
- 8cb1cea: The workspace blocklist, `blocked_senders` (REST `/meta/v1/blocked-senders`, MCP tools `blocked_senders_*`, CLI `vibase blocked-senders list|get|create|delete`): an owner, signed in, blocks addresses and domains for every mailbox of the workspace and lifts them again; anyone holding the new `blocked_senders:read` scope reads the list. `blocked_senders:write` is owner-only and not agent-grantable; the list is not proposable. Every change emits `blocked_sender.created` or `blocked_sender.deleted`. Capture does not apply the list yet.
- 38965d0: Email capture now applies sender filters per mailbox, going forward: a message is skipped before anything of it is stored when any other party matches the blocklist (an address, or a domain with its subdomains), and, when the mailbox opted in, when the sender is a group address (`support@`, `noreply@`) or a personal-mail domain (gmail.com). Mail already captured stays.
- d19a20c: Migration `0023_forms.sql`: the `forms` table (website forms and their field mapping), with `form_allowed_origins` and `form_tags`, and a new owner-only `forms` resource on `/meta/v1/forms` (list, get, create, update, delete; `forms:read` for members, `forms:write` for owners, signed in). Each form is created with its own credential-less agent. Nothing receives a submission yet.
- c8d2ff8: Migration `0024_form_channel.sql`: the capture tables accept channel `form` and a form is a message or thread source (`threads`, `messages`, `interactions`, `message_sources` and `thread_sources` are rebuilt; every row is kept). The `channel` filter of `threads`, `messages` and `interactions` lists now accepts `form` (empty until the public form route ships). No behaviour change for Gmail capture; apply the migration with `vibase-server upgrade` or `db:migrate:remote`.
- 8e42a1b: A form's agent is now managed by its form: `agents.update` and `api_keys.create` refuse it with `409 form_principal`, renaming a form renames its agent, and deleting a form disables it, each in the form's own unit with an `agent.updated` event before the form's event.
- 1edf05b: A form now carries its allowed origins and tags: `forms.create` and `forms.update` take `allowed_origins` (at most 20 normalised https origins) and `tag_ids` (at most 20 live tags), each replaced whole, and `forms.get`, `forms.list` and the `form.*` events show both lists.
- 051da8d: The form submission capture unit (dormant, no route yet): given a form and a submission's fields, the vault picks the submitter (email, else phone), checks the workspace blocklist, stores the content and records one inbound `form` interaction on the submitter's contact as the form's principal, with every event. An existing contact is only added to (a null name is filled, the form's tags are linked). No behaviour change until the public form route ships.
- 866c5a7: The public form ingress handler (`handleFormIngress` in `@vibase/api`): answers `POST /f/{public_id}` and its CORS preflight from a request and injected Turnstile and rate-limit ports, in the order of the spec (limits, form, origin, validation, honeypot, blocklist, Turnstile, capture), with the uniform `202` for accepted, honeypot and blocked submissions. Not routed yet: no deployed behaviour changes until the Worker serves `/f/*`.
- 8e53a55: The Worker answers `POST /f/{public_id}` and its `OPTIONS` preflight: the public website-form endpoint. It needs no authentication and sits behind the migration, configuration, control and deployment-marker gates. A submission is checked against the form's allowed origins and a Cloudflare Turnstile token (`TURNSTILE_SECRET_KEY`, a Worker secret; without it the route answers `503 challenge_unavailable`), rate limited by the new `FORM_IP_LIMITER` (10 a minute per IP and form) and `FORM_LIMITER` (60 a minute per form) `ratelimits` bindings declared in `wrangler.jsonc` (skipped when a binding is absent; needs wrangler 4.36 or later), and captured as a `form` thread, message and interaction. The route is documented in the docs (Website forms) and is not in OpenAPI or MCP. The `channel` column descriptions now name `email` and `form`.
- ae1c6e4: The control-plane database is required in every auth mode. The Worker answers `500` on every non-health request without a `CONTROL_DB` binding, `503 migrations_pending` while its migrations are behind, and refuses a control database not paired with its CRM database, whatever `AUTH_PROVIDER` is (it was `better-auth` only). `audit.list` is served on Clerk and unset instances too. The remote scripts (`db:migrate:remote`, `db:status:remote`, `deploy:remote`, `bootstrap --remote`) and `vibase-server status` and `upgrade` refuse an instance with no control database before any call, pointing at `setup:remote` or `vibase-server setup`; local `bootstrap` pairs the control marker in every mode and refuses a local environment with no control database.
- 4a8644d: Every API key the bootstrap makes now lives in the control-plane database, with its `api_key.created` audit row, and none in the CRM database: `bootstrap` (local and `--remote`), `vibase-server setup` and `setup:remote` write the operator key there, and a bootstrap that would make a key without a control database is refused before either database is written. If the control write fails after the CRM rows commit, the run fails naming the organisation and the agent, and the key is made with `api_keys.create`.
- 132eb70: Migration `0022_unattached_identities.sql`: an identity may now be neither own nor a contact's (`contact_id` null, `own` false), the state a captured address takes when the contact policy does not qualify it. `identities.resolve` promotes such an identity to a new contact when it finds one. Nothing creates an unattached identity yet: capture behaves as before.
- 61bf3ba: Mail capture now applies each mailbox's `contact_creation` setting: with `sent` or `none`, addresses the setting does not qualify are recorded without a contact, and a later qualifying capture gives them one.
- dcd7100: Migration `0025_capture_defaults.sql`: a new Gmail connection defaults to `contact_creation: sent` with `exclude_group_addresses` and `exclude_personal_domains` on (`channel_connections` is rebuilt for the new column defaults; every existing connection keeps its settings). Previously new connections created a contact for every correspondent and excluded nothing. Change an existing connection with `vibase connections update <id> --contact-creation sent --exclude-group-addresses --exclude-personal-domains`. Apply the migration with `vibase-server upgrade` or `db:migrate:remote`.
- 8e8425c: `vibase-server setup` (and the source `setup:remote`) now defaults a new instance to Better Auth (`--auth better-auth|clerk|none`). It writes `AUTH_PROVIDER` and `PUBLIC_BASE_URL` (no Clerk variable), generates `AUTH_SECRET` once into the instance's secrets file and puts it on the Worker (never rotated by setup), puts an optional `AUTH_GOOGLE_CLIENT_ID`/`AUTH_GOOGLE_CLIENT_SECRET` pair from the same file, bootstraps the instance (marker `better-auth:<env>`, control marker, the `vibase-cli` client, the owner invitation) and prints the owner invitation link once. A re-run never re-issues the link: an existing owner or a pending invitation is reported, nothing is issued. An instance that already has a record keeps its recorded provider (an absent `AUTH_PROVIDER` means `none`), and an `--auth` that differs from the record is refused before any step. Pass `--auth clerk` to keep a Clerk install.
- cba93d5: Owner recovery. `vibase-server owner-reset --env <name> [--email <owner>] [--dry-run]` (and, from a source checkout, `CONFIRM_REMOTE=1 pnpm -C packages/server-d1 bootstrap -- --remote --env <name> --owner-reset`) prints a one-time Better Auth reset link for an owner who lost their password, once and stored nowhere, with an audit row that never holds the link; it needs the instance's Cloudflare credentials and the `AUTH_SECRET` in the secrets file. With no owner at all it issues an owner invitation for `--email` instead. Owner invitations are now replaced in one set-based control batch with no read first (bootstrap's re-run uses it too), and a refused replace writes nothing. The no-email statement setup prints gains its owner sentence, and setup's "owner invitation pending" line names the command that issues a new link.
- 0f21d9d: `vibase-server setup` (and the source `setup:remote`) takes `--workers-dev` as an alternative to `--api-host`: an operator with no domain gets an instance on `<worker>.<subdomain>.workers.dev`, derived from the account's workers.dev subdomain (Better Auth or `--auth none`; refused with Clerk). With no subdomain registered setup refuses and names the dashboard path; `--register-workers-subdomain <name>` registers one, once, only when passed and never on a dry run. The settings file gains `workers_dev`; the generated config has no custom-domain route in workers.dev mode. `--api-host <new> --change-host` moves a recorded instance to a custom domain (or between two), prints what the move breaks (sign in again, `vibase login` again, reconnect MCP clients, the new Google redirect URI) and replaces the old route. A host that differs from the record is refused without `--change-host`. The verify step shares one 300 s deadline for the health wait and both discovery reads, and every URL of a run uses one base URL.
- 38f8424: New `vibase-server init`: asks for (or takes as flags) the instance's name, API host, owner email and auth and email providers, then writes its secrets file with mode 600, never over an existing file, with the generated secrets in and an empty line for each value you supply, and prints the `setup --dry-run` command to run next. `vibase-server setup` now turns Gmail off, with a header line naming the two Google client values, when neither is set, instead of refusing a file that holds only the generated Gmail keys; its "no secrets file" refusal points at `init`.
- 118658b: `vibase-server init` also writes the instance's settings file (`<env>.json`, marked `stage: "init"`) with the API host, the auth provider and the owner email, and prints `vibase-server setup --env <env>` (plus `--secrets-file` when given) as the next command. `vibase-server setup` takes the host, provider and owner email from that file, or from an instance's record, when the flags leave them out, and refuses a flag that differs; `--api-host` or `--workers-dev` is optional for a recorded instance. `config:write` adopts init's file as the full record, which now also keeps `owner_email`. `status`, `upgrade`, `redeploy` and `owner-reset` refuse an init-written file with "not set up yet". Re-running `init` replaces its own settings file until setup has run once.
- 711f0c2: `vibase-server redeploy --env <name>` puts the installed package's build on an instance whatever is live: a new build of the same version, the same build again, or an older package as a rollback. It applies only the migrations the instance lacks, never reverses one, and refuses no version or schema. `upgrade` no longer calls a same-version, different build "nothing to do": it stops, naming both commits and `redeploy`, and `status` reports it too. `upgrade --rollback` is removed in favour of `redeploy`, and `upgrade` and `redeploy` now wait for the new commit on `/health`, not only the version.
- e5c67e9: `vibase-server setup` verifies through the Cloudflare API and no longer waits. Verify checks the Worker (this release's version and commit, and every recorded variable), its secrets by name, the custom domain or workers.dev subdomain, both migration trackers and the R2 bucket, and fails at the first check that does not hold. It then makes one 10 second request to `/health`: a host that does not answer yet (a new custom domain whose DNS has not propagated) is reported as `not reachable yet` and the run still succeeds; a wrong answer fails. The discovery checks run once, after a `200`. Setup never contacts the host before verify (the newer-release refusal and the deploy skip read the Worker's settings through the API). The output ends with the owner invitation, or a block saying why none was issued and how to get one (`vibase-server owner-reset`), and, for a custom domain that did not answer, a note about DNS propagation. `upgrade`, `redeploy` and `status` say `cannot resolve <host> from this machine (DNS)` when the name does not resolve.
- da31f8e: New variable `AUTH_TRUSTED_ORIGINS` (a comma-separated list of first-party app origins, read only with `AUTH_PROVIDER=better-auth`). Each listed origin is trusted by Better Auth (cookie-bearing POSTs such as sign-out, and `callbackURL`), gets credentialed CORS on `/auth/*` only, and is a place `/sign-in?return_to=` can send a person back to after they sign in. `/api`, `/meta` and `/mcp` are unchanged: an app that also calls `/api` stays in `CORS_ALLOWED_ORIGINS`. Empty or unset changes nothing; a malformed value makes the Worker answer `500 internal`.
- 13ca7bf: The sign-in, invitation, password reset, consent and device pages are rebuilt on React and the shadcn-based component set, with Tailwind's stylesheet. Same paths, text, flows and security headers; the look follows shadcn's neutral theme. `/connect` is unchanged.

Read and propose start on and write off, `audit:read` starts off, sign-in access is a fixed line, and Allow grants only what is switched on.
- 16fbb75: The workspace app has an Agents page at `/agents`: every agent of the workspace with its status, how it connected, its permissions and dates, an owner's confirmed Disable and Enable, the agents of website forms labelled and left to their form, and the Connect an agent instructions below. The sidebar shows it to people who can read agents.

Signing in from the app on Better Auth still lands on `/connect` until the sign-in returns ship.

### Patch Changes

- a6b3eed: The `api_key` event type leaves the event feed. Historic `api_key.created` and `api_key.revoked` rows are no longer returned by `events.list` or `events.get` (nothing has written them since API keys moved to the control plane), and `webhooks.create` and `webhooks.update` refuse an `api_key.*` event type with `400 unknown_event_type`. Key issue and revoke are recorded in the audit log: read them with `audit.list` (`audit:read`).
- ae17375: A message's content fields (`preview`, `attachments`) are now declared on the `messages` resource and shown only to a caller with `messages:read`: the record schema in the OpenAPI document marks them optional, and `schema.get` lists them under the resource's `content` key. Every caller today holds `messages:read`, so records, events and webhook payloads are unchanged.
- bac1e37: The scope grammar accepts the action `read_metadata` and a scope set closes `x:read` to `x:read_metadata` wherever the vault declares it. Nothing declares one yet, so no grant or token can carry it and every caller sees what it saw before; asking for `messages:read_metadata` is refused as an undeclared scope.
- 7d75c10: A cold Worker answers an unauthenticated `POST /mcp` (the 401 and its challenge), the two protected-resource documents and the authorization-server metadata from its variables alone, before it loads the application or reads a database, so Claude's 5-second connector check no longer times out on a fresh isolate. On a fresh deploy the `/mcp` 401 went from about 0.5 s to 0.14 s and the metadata from 0.6 s to 0.07 s (from a colo next to the database; the saving grows with the distance to it). Built-in provider only; every other request, and any request with a credential, takes the full path as before.
- 024d7a0: Invitations in the control plane. Control migration `0002` adds `invitations` and the append-only `control_audit` to the control database. Owners create, list and revoke invitations (`invitations.create|list|revoke`, owner-held human-only scopes `invitations:read|write`; the link is shown once and only its SHA-256 is stored). `bootstrap --auth-provider better-auth --owner-email <email>` issues the first owner invitation and prints its URL once; a re-run with no owner replaces it. The links are inert until invitation-gated sign-up lands.
- de69bda: Optional auth email. With the `EMAIL` (`send_email`) binding and an `AUTH_EMAIL_FROM` variable both present on the built-in provider, `invitations.create` emails the invitation (the new `delivery` field defaults to `email` and the answer has no `url`; `delivery: "link"` returns the link as before; `email` while email is off is `501 email_not_configured`; a failed send revokes the invitation and answers `502 email_send_failed`). Accepting an emailed invitation records the address as verified. `invitations.list` returns `delivery`. Control migration `0003` adds `invitations.delivery` (existing rows are `link`): run `vibase-server upgrade` before using it. One variable without the other, or a malformed address, fails closed. With neither, nothing changes.
- c2747c0: Read the control-plane audit log. `audit.list` (`GET /meta/v1/audit`, MCP tool `audit_list`, `vibase audit list`) browses `control_audit` (invitations created, revoked and accepted, sessions revoked on removal, reset links issued) oldest first, filtered by exact `action`, `target_type` and `target_id`, paged by `limit` (1 to 200, default 50) and `after`/`next_cursor`. New scope `audit:read`: held by every owner, never by a member, and an owner may grant it to an agent; it is not in any default grant (the bootstrap agent, Clerk's default scopes, the registration default list). A deployment without a control-plane database answers `501 provider_not_configured`. Reading writes nothing. Clerk instances gain the scope in their catalog when `setup:remote` is next run.
- 7f02a06: Built-in auth clients and discovery. `bootstrap --auth-provider better-auth --public-base-url <origin>` seeds the first-party `vibase-cli` client into the control database (idempotent; no human is created). Open dynamic client registration is limited to public clients, the agent-grantable scopes and the API and MCP resources, 10 registrations per IP per hour. `/.well-known/vibase` carries `resource` on `better-auth`, the protected-resource documents and the RFC 8414 document at `/.well-known/oauth-authorization-server/auth` name `PUBLIC_BASE_URL`. `vibase login` finds a path issuer by RFC 8414 path insertion (appended form only on a non-200) and sends `resource` on device authorization, polling and refresh when discovery names one.
- 3076c7a: Invitation-gated sign-up on the built-in provider. `POST /auth/sign-up/email` creates an account only when its body carries `invitation_token` for a live invitation of that email; every other attempt is `403 invitation_required`. Signing up accepts the invitation: the vault writes the user (or, for an agent invitation, an agent account with no scopes) and the membership with their events, then the invitation is marked accepted with an `invitation.accepted` audit row. An account left without its vault rows is repaired on its next sign-in while the invitation that admitted it is still live.
