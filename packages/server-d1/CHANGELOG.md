# @vibase/server-d1

## 0.2.0

### Minor Changes

- f523d42: The API key operations (`api_keys.create`, `revoke`, `list`, `get`) now run on the control-plane database: a create or revoke writes its `control_audit` row and no `api_key.*` event, and keys held only in the CRM database by an earlier version are not listed, read or revocable through them (none are in use; they still authenticate until the CRM key table is retired).
- 40213d3: The workspace app at `/home`, `/accounts` and `/agents` is now a single-page app: moving between its pages no longer reloads the browser, and the sign-in session and workspace are read once per visit. Deep links and refresh work as before, and the window title and the current sidebar entry follow the page.
- a39dd68: Migration `0021_capture_settings.sql`: every connection stores its capture settings. `channel_connections` gains `exclude_group_addresses`, `exclude_personal_domains` and `contact_creation`; new tables `connection_capture_labels` (INBOX and SENT for every existing connection), `connection_blocked_senders` and `blocked_senders` (the workspace blocklist, not yet writable). The connection record (`connections.get`, `connections.list`, `connection.created`) now carries `capture_labels`, `blocked_senders` and the three scalars. Defaults change nothing: capture and contact creation behave as before.
- 0f29f3c: `connections.update` (`PATCH /meta/v1/connections/{id}`, MCP tool `connections_update`, CLI `vibase connections update <id>`): the owner of a connection, signed in, changes its capture settings (labels, blocked senders, group-address and personal-domain exclusion, contact creation) in one call. A list replaces the whole list; every accepted call emits one `connection.updated`. The `connections:write` scope now reads "Connect and disconnect mailboxes, and change their capture settings".
- 8cb1cea: The workspace blocklist, `blocked_senders` (REST `/meta/v1/blocked-senders`, MCP tools `blocked_senders_*`, CLI `vibase blocked-senders list|get|create|delete`): an owner, signed in, blocks addresses and domains for every mailbox of the workspace and lifts them again; anyone holding the new `blocked_senders:read` scope reads the list. `blocked_senders:write` is owner-only and not agent-grantable; the list is not proposable. Every change emits `blocked_sender.created` or `blocked_sender.deleted`. Capture does not apply the list yet.
- 38965d0: Email capture now applies sender filters per mailbox, going forward: a message is skipped before anything of it is stored when any other party matches the blocklist (an address, or a domain with its subdomains), and, when the mailbox opted in, when the sender is a group address (`support@`, `noreply@`) or a personal-mail domain (gmail.com). Mail already captured stays.
- d19a20c: Migration `0023_forms.sql`: the `forms` table (website forms and their field mapping), with `form_allowed_origins` and `form_tags`, and a new owner-only `forms` resource on `/meta/v1/forms` (list, get, create, update, delete; `forms:read` for members, `forms:write` for owners, signed in). Each form is created with its own credential-less agent. Nothing receives a submission yet.
- c8d2ff8: Migration `0024_form_channel.sql`: the capture tables accept channel `form` and a form is a message or thread source (`threads`, `messages`, `interactions`, `message_sources` and `thread_sources` are rebuilt; every row is kept). The `channel` filter of `threads`, `messages` and `interactions` lists now accepts `form` (empty until the public form route ships). No behaviour change for Gmail capture; apply the migration with `vibase-server upgrade` or `db:migrate:remote`.
- 8e42a1b: A form's agent is now managed by its form: `agents.update` and `api_keys.create` refuse it with `409 form_principal`, renaming a form renames its agent, and deleting a form disables it, each in the form's own unit with an `agent.updated` event before the form's event.
- 1edf05b: A form now carries its allowed origins and tags: `forms.create` and `forms.update` take `allowed_origins` (at most 20 normalised https origins) and `tag_ids` (at most 20 live tags), each replaced whole, and `forms.get`, `forms.list` and the `form.*` events show both lists.
- 051da8d: The form submission capture unit (dormant, no route yet): given a form and a submission's fields, the vault picks the submitter (email, else phone), checks the workspace blocklist, stores the content and records one inbound `form` interaction on the submitter's contact as the form's principal, with every event. An existing contact is only added to (a null name is filled, the form's tags are linked). No behaviour change until the public form route ships.
- 866c5a7: The public form ingress handler (`handleFormIngress` in `@vibase/api`): answers `POST /f/{public_id}` and its CORS preflight from a request and injected Turnstile and rate-limit ports, in the order of the spec (limits, form, origin, validation, honeypot, blocklist, Turnstile, capture), with the uniform `202` for accepted, honeypot and blocked submissions. Not routed yet: no deployed behaviour changes until the Worker serves `/f/*`.
- 8e53a55: The Worker answers `POST /f/{public_id}` and its `OPTIONS` preflight: the public website-form endpoint. It needs no authentication and sits behind the migration, configuration, control and deployment-marker gates. A submission is checked against the form's allowed origins and a Cloudflare Turnstile token (`TURNSTILE_SECRET_KEY`, a Worker secret; without it the route answers `503 challenge_unavailable`), rate limited by the new `FORM_IP_LIMITER` (10 a minute per IP and form) and `FORM_LIMITER` (60 a minute per form) `ratelimits` bindings declared in `wrangler.jsonc` (skipped when a binding is absent; needs wrangler 4.36 or later), and captured as a `form` thread, message and interaction. The route is documented in the docs (Website forms) and is not in OpenAPI or MCP. The `channel` column descriptions now name `email` and `form`.
- ae1c6e4: The control-plane database is required in every auth mode. The Worker answers `500` on every non-health request without a `CONTROL_DB` binding, `503 migrations_pending` while its migrations are behind, and refuses a control database not paired with its CRM database, whatever `AUTH_PROVIDER` is (it was `better-auth` only). `audit.list` is served on Clerk and unset instances too. The remote scripts (`db:migrate:remote`, `db:status:remote`, `deploy:remote`, `bootstrap --remote`) and `vibase-server status` and `upgrade` refuse an instance with no control database before any call, pointing at `setup:remote` or `vibase-server setup`; local `bootstrap` pairs the control marker in every mode and refuses a local environment with no control database.
- 4a8644d: Every API key the bootstrap makes now lives in the control-plane database, with its `api_key.created` audit row, and none in the CRM database: `bootstrap` (local and `--remote`), `vibase-server setup` and `setup:remote` write the operator key there, and a bootstrap that would make a key without a control database is refused before either database is written. If the control write fails after the CRM rows commit, the run fails naming the organisation and the agent, and the key is made with `api_keys.create`.
- 132eb70: Migration `0022_unattached_identities.sql`: an identity may now be neither own nor a contact's (`contact_id` null, `own` false), the state a captured address takes when the contact policy does not qualify it. `identities.resolve` promotes such an identity to a new contact when it finds one. Nothing creates an unattached identity yet: capture behaves as before.
- 61bf3ba: Mail capture now applies each mailbox's `contact_creation` setting: with `sent` or `none`, addresses the setting does not qualify are recorded without a contact, and a later qualifying capture gives them one.
- dcd7100: Migration `0025_capture_defaults.sql`: a new Gmail connection defaults to `contact_creation: sent` with `exclude_group_addresses` and `exclude_personal_domains` on (`channel_connections` is rebuilt for the new column defaults; every existing connection keeps its settings). Previously new connections created a contact for every correspondent and excluded nothing. Change an existing connection with `vibase connections update <id> --contact-creation sent --exclude-group-addresses --exclude-personal-domains`. Apply the migration with `vibase-server upgrade` or `db:migrate:remote`.
- 8e8425c: `vibase-server setup` (and the source `setup:remote`) now defaults a new instance to Better Auth (`--auth better-auth|clerk|none`). It writes `AUTH_PROVIDER` and `PUBLIC_BASE_URL` (no Clerk variable), generates `AUTH_SECRET` once into the instance's secrets file and puts it on the Worker (never rotated by setup), puts an optional `AUTH_GOOGLE_CLIENT_ID`/`AUTH_GOOGLE_CLIENT_SECRET` pair from the same file, bootstraps the instance (marker `better-auth:<env>`, control marker, the `vibase-cli` client, the owner invitation) and prints the owner invitation link once. A re-run never re-issues the link: an existing owner or a pending invitation is reported, nothing is issued. An instance that already has a record keeps its recorded provider (an absent `AUTH_PROVIDER` means `none`), and an `--auth` that differs from the record is refused before any step. Pass `--auth clerk` to keep a Clerk install.
- cba93d5: Owner recovery. `vibase-server owner-reset --env <name> [--email <owner>] [--dry-run]` (and, from a source checkout, `CONFIRM_REMOTE=1 pnpm -C packages/server-d1 bootstrap -- --remote --env <name> --owner-reset`) prints a one-time Better Auth reset link for an owner who lost their password, once and stored nowhere, with an audit row that never holds the link; it needs the instance's Cloudflare credentials and the `AUTH_SECRET` in the secrets file. With no owner at all it issues an owner invitation for `--email` instead. Owner invitations are now replaced in one set-based control batch with no read first (bootstrap's re-run uses it too), and a refused replace writes nothing. The no-email statement setup prints gains its owner sentence, and setup's "owner invitation pending" line names the command that issues a new link.
- 0f21d9d: `vibase-server setup` (and the source `setup:remote`) takes `--workers-dev` as an alternative to `--api-host`: an operator with no domain gets an instance on `<worker>.<subdomain>.workers.dev`, derived from the account's workers.dev subdomain (Better Auth or `--auth none`; refused with Clerk). With no subdomain registered setup refuses and names the dashboard path; `--register-workers-subdomain <name>` registers one, once, only when passed and never on a dry run. The settings file gains `workers_dev`; the generated config has no custom-domain route in workers.dev mode. `--api-host <new> --change-host` moves a recorded instance to a custom domain (or between two), prints what the move breaks (sign in again, `vibase login` again, reconnect MCP clients, the new Google redirect URI) and replaces the old route. A host that differs from the record is refused without `--change-host`. The verify step shares one 300 s deadline for the health wait and both discovery reads, and every URL of a run uses one base URL.
- 711f0c2: `vibase-server redeploy --env <name>` puts the installed package's build on an instance whatever is live: a new build of the same version, the same build again, or an older package as a rollback. It applies only the migrations the instance lacks, never reverses one, and refuses no version or schema. `upgrade` no longer calls a same-version, different build "nothing to do": it stops, naming both commits and `redeploy`, and `status` reports it too. `upgrade --rollback` is removed in favour of `redeploy`, and `upgrade` and `redeploy` now wait for the new commit on `/health`, not only the version.
- da31f8e: New variable `AUTH_TRUSTED_ORIGINS` (a comma-separated list of first-party app origins, read only with `AUTH_PROVIDER=better-auth`). Each listed origin is trusted by Better Auth (cookie-bearing POSTs such as sign-out, and `callbackURL`), gets credentialed CORS on `/auth/*` only, and is a place `/sign-in?return_to=` can send a person back to after they sign in. `/api`, `/meta` and `/mcp` are unchanged: an app that also calls `/api` stays in `CORS_ALLOWED_ORIGINS`. Empty or unset changes nothing; a malformed value makes the Worker answer `500 internal`.
- 13ca7bf: The sign-in, invitation, password reset, consent and device pages are rebuilt on React and the shadcn-based component set, with Tailwind's stylesheet. Same paths, text, flows and security headers; the look follows shadcn's neutral theme. `/connect` is unchanged.
- 615830a: The consent page groups the permissions an app asks for into areas (CRM records, Messages, Activity and approvals, Integrations, Administration) with Read, Propose changes for approval and Write switches. Read and propose start on and write off, `audit:read` starts off, sign-in access is a fixed line, and Allow grants only what is switched on.
- 16fbb75: The workspace app has an Agents page at `/agents`: every agent of the workspace with its status, how it connected, its permissions and dates, an owner's confirmed Disable and Enable, the agents of website forms labelled and left to their form, and the Connect an agent instructions below. The sidebar shows it to people who can read agents.
- 42b696d: The workspace app is served. `GET /home` on any instance (Clerk, Better Auth or no provider) answers the app: a shell with a Home page ("Welcome to your CRM" and who you are: name, email, role and workspace), on the same session `/connect` uses. `GET /` redirects to `/home`. The release package gains `assets/app/` (`index.html`, `app.js`, `app.css`) and `wrangler.base.jsonc`'s `assets.run_worker_first` gains `/`, `/home`, `/app` and `/app/*`, so an instance upgrade needs the new base config. The app and `/connect` are served under one Content-Security-Policy that allows runtime `<style>` elements (`style-src 'self' 'unsafe-inline'`; `script-src` is unchanged), so `/connect`'s policy changes on Better Auth and with no provider; the sign-in, consent and device pages keep their stricter policy. Signing in from the app on Better Auth still lands on `/connect` until the sign-in returns ship.
- 1924453: Signing in or accepting an invitation now lands on `/home`, or on the app page the person came from; Home shows a Get started section with a Connect an agent prompt (login command, MCP URL, API-key line and a Check again button) until an enabled agent is connected.
- 8e95ad3: The workspace app gains the **Connected accounts** page at `/accounts`, with its sidebar row (shown to anyone who can read connections). It lists the workspace's mailboxes in two sections, Your mailboxes and Other mailboxes, with each mailbox's address and status. **Connect Gmail** starts the Google consent flow, and **Reconnect** on your own mailbox that needs it; the page also shows the outcome the Gmail callback returns (`connection_id` or `error` in the query) and then removes it from the URL. `/accounts` is served, and accepted as a sign-in return target, wherever `/home` is; the packaged `wrangler.jsonc` lists it in `run_worker_first`. `@vibase/api` exports the callback's error sentences as `CONNECT_ERROR_TEXT`.
- 15438d9: The workspace app's Connected accounts page (`/accounts`) gains a mailbox settings view (`/accounts?connection=<id>`): the owner edits the mailbox's capture labels, blocked senders, group-address and personal-domain filters and contact creation and saves them in one step; everyone else reads them. Every mailbox row offers Settings, Disconnect (after a confirmation that says captured mail stays) and, on connected mailboxes, Sync now.
- 5e24d7d: The Gmail connect flow returns to the instance's own Connected accounts page. With `CONNECT_RETURN_URL` unset and the app served, the callback now redirects to `<PUBLIC_BASE_URL or the request's origin>/accounts` (with `connection_id` on success or `error=<code>` on a refusal) instead of showing the built-in result page; a set `CONNECT_RETURN_URL` still wins, and an instance without the app keeps the built-in page. Home's Get started now offers **Connect your email**, a link to Connected accounts, to a person who may connect a mailbox and owns none.

### Patch Changes

- a6b3eed: The `api_key` event type leaves the event feed. Historic `api_key.created` and `api_key.revoked` rows are no longer returned by `events.list` or `events.get` (nothing has written them since API keys moved to the control plane), and `webhooks.create` and `webhooks.update` refuse an `api_key.*` event type with `400 unknown_event_type`. Key issue and revoke are recorded in the audit log: read them with `audit.list` (`audit:read`).
- 024d7a0: Invitations in the control plane. Control migration `0002` adds `invitations` and the append-only `control_audit` to the control database. Owners create, list and revoke invitations (`invitations.create|list|revoke`, owner-held human-only scopes `invitations:read|write`; the link is shown once and only its SHA-256 is stored). `bootstrap --auth-provider better-auth --owner-email <email>` issues the first owner invitation and prints its URL once; a re-run with no owner replaces it. The links are inert until invitation-gated sign-up lands.
- de69bda: Optional auth email. With the `EMAIL` (`send_email`) binding and an `AUTH_EMAIL_FROM` variable both present on the built-in provider, `invitations.create` emails the invitation (the new `delivery` field defaults to `email` and the answer has no `url`; `delivery: "link"` returns the link as before; `email` while email is off is `501 email_not_configured`; a failed send revokes the invitation and answers `502 email_send_failed`). Accepting an emailed invitation records the address as verified. `invitations.list` returns `delivery`. Control migration `0003` adds `invitations.delivery` (existing rows are `link`): run `vibase-server upgrade` before using it. One variable without the other, or a malformed address, fails closed. With neither, nothing changes.
- c2747c0: Read the control-plane audit log. `audit.list` (`GET /meta/v1/audit`, MCP tool `audit_list`, `vibase audit list`) browses `control_audit` (invitations created, revoked and accepted, sessions revoked on removal, reset links issued) oldest first, filtered by exact `action`, `target_type` and `target_id`, paged by `limit` (1 to 200, default 50) and `after`/`next_cursor`. New scope `audit:read`: held by every owner, never by a member, and an owner may grant it to an agent; it is not in any default grant (the bootstrap agent, Clerk's default scopes, the registration default list). A deployment without a control-plane database answers `501 provider_not_configured`. Reading writes nothing. Clerk instances gain the scope in their catalog when `setup:remote` is next run.
- 7f02a06: Built-in auth clients and discovery. `bootstrap --auth-provider better-auth --public-base-url <origin>` seeds the first-party `vibase-cli` client into the control database (idempotent; no human is created). Open dynamic client registration is limited to public clients, the agent-grantable scopes and the API and MCP resources, 10 registrations per IP per hour. `/.well-known/vibase` carries `resource` on `better-auth`, the protected-resource documents and the RFC 8414 document at `/.well-known/oauth-authorization-server/auth` name `PUBLIC_BASE_URL`. `vibase login` finds a path issuer by RFC 8414 path insertion (appended form only on a non-200) and sends `resource` on device authorization, polling and refresh when discovery names one.
- 3076c7a: Invitation-gated sign-up on the built-in provider. `POST /auth/sign-up/email` creates an account only when its body carries `invitation_token` for a live invitation of that email; every other attempt is `403 invitation_required`. Signing up accepts the invitation: the vault writes the user (or, for an agent invitation, an agent account with no scopes) and the membership with their events, then the invitation is marked accepted with an `invitation.accepted` audit row. An account left without its vault rows is repaired on its next sign-in while the invitation that admitted it is still live. Invitation links from `bootstrap --owner-email` and `invitations.create` now work.
- 200c676: Membership writes and owner-issued reset links on the built-in provider. Owners (new owner-held, human-only scope `members:write`) change a member's role (`memberships.update`, `vibase memberships update <id> --role member`) or remove a member (`memberships.delete`, a soft delete): removing or demoting the last owner is `409 last_owner`, decided in the write's own statement. A removed member is denied at once (roles are read per request); the vault then revokes that person's sessions, OAuth access and refresh tokens and pending device codes and records a `user.sessions_revoked` audit row. `users.issue_reset_link` (`vibase users issue-reset-link --user-id <id>`) returns a one-time password reset link for a member, valid for one hour and shown once, with a `user.reset_link_issued` audit row; the public `POST /auth/request-password-reset` stays refused while email is off. On Clerk and on Postgres these operations answer `501 provider_not_configured`.
- 8380693: Control-plane repair sweep. On a `better-auth` instance the one-minute rail cron now revokes the sessions, OAuth tokens and device codes of any linked account that has lost its authority (a removed member, a disabled agent), and deletes accounts older than 24 hours that no CRM user or agent names and no invitation admitted. `vibase-server status` and `db:status:remote` print, after the control database's migration diff, how many subjects and orphan accounts the next sweep would act on (`[control] sweep: ...`); the counts never change the exit code. No migration.
- 6f30ee5: Google sign-in on the built-in provider. With a complete Google client (`AUTH_GOOGLE_CLIENT_ID` and `AUTH_GOOGLE_CLIENT_SECRET`, else the Gmail client's `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`; half of the `AUTH_GOOGLE_*` pair fails closed naming the variable) `/sign-in` and `/invite` show a "Continue with Google" button, and `/.well-known/vibase`'s `better-auth` block gains `sign_in_methods` (`["password"]` or `["password","google"]`). Google signs in an existing account whose email Google reports verified and equal; a new account is created only through a live invitation for the Google-verified email (the token rides Better Auth's OAuth state, never a URL), else the callback returns to `/sign-in?error=invitation_required`. The vault user's `email_verified` follows the Better Auth user. The redirect URI to register on the Google client is `<PUBLIC_BASE_URL>/auth/callback/google`.
- d21ca33: Re-admit a removed member on the built-in provider. After an owner removes a member, inviting the same address again now works: the person signs in (password, with the invitation token in the `vibase-invitation` header, or Google, through the existing sign-in button) and gets a new membership with the invitation's role; the removed membership stays as history. A token that does not re-admit (unknown, expired, revoked, another address, an agent invitation, or a person who is already a member) is ignored and the sign-in kept. The `/invite` page gains an "Already have an account? Sign in to accept" mode. No migration.
- a6a9cca: Self-service password reset by email. With email configured (`EMAIL` binding and `AUTH_EMAIL_FROM`) on the built-in provider, `POST /auth/request-password-reset` is open (5 requests per hour per client IP), emails a one-hour reset link to a known address and answers the same for an unknown one (the send runs after the response); `/.well-known/vibase`'s `auth` block gains `self_service_reset`, and `/sign-in` shows "Forgot password?" when it is `true`. Owner-issued reset links are unchanged and never emailed; with email off nothing changes. A failed invitation or reset send now logs one line (event name and error code only), and the `502 email_send_failed` message no longer claims the invitation was dropped when the compensating revoke also failed.
- ba8d77d: Control migration `0004` creates the four webhook tables (`webhook_subscriptions`, `webhook_secrets`, `webhook_dispatch_state`, `webhook_deliveries`) in the control database, with a control-store module for them. Dormant: nothing reads or writes them yet, and the webhook operations still use the CRM tables.
- babfb4d: Control migration 0005 adds an empty, dormant `api_keys` table to the control database (nothing reads or writes it yet).
- 42a4ce1: API keys are authenticated against the control plane first. The Worker looks a key's hash up in control `api_keys`, reads its revocation, expiry and agent on every request (only the immutable key-to-agent mapping is cached per isolate), stamps `last_used_at` in control, and falls back to the CRM database's keys when control has none. No key is created in control yet, so existing keys keep working through the fallback.
- da333e4: CRM migration 0020 drops the `api_keys`, `webhook_subscriptions`, `webhook_secrets`, `webhook_dispatch_state` and `webhook_deliveries` tables from the CRM database; API keys and webhook subscriptions live only in the control database, where they have lived since the control-plane move. `schema.get` no longer lists them. API-key authentication reads the control database only, so a key whose hash control does not hold is refused, and `bootstrap` refuses to run without a control key store. Upgrade with `vibase-server upgrade`; rows in the dropped CRM tables go with them (they were unused).
- 27cdbcf: A finished sign-in (password, Google, or an invitation claim) now continues to `/connect` instead of stopping on the `/sign-in` "Signed in" view; a valid `return_to` such as `/device` is still honoured, including through Google sign-in.
- 490e0ef: The /invite page now reads top to bottom: Continue with Google, an OR divider, the Create a new account form with a full-width button, then an "Already have an account? Sign in to accept" link.
- 244fca6: `setup:remote --replace-instance <env>` (checkout-only) builds a fresh Better Auth instance on the `vb-` names in place of a recorded one, leaving the old resources untouched. The shared refusal texts for a provider change and a rename now point at it; `vibase-server setup` does not take the flag.
- cc2376c: CRM migration 0019 drops the dormant `auth_*` tables (they live in the control database now). The package ships `control-migrations/` under the new export `./control-migrations/*`, listed in `release.json` as `control_migrations`.
- f1aeec1: `vibase-server status` and `upgrade` handle an instance's control-plane database beside its CRM database. The instance settings take an optional `control_d1` (`name` and `id`, recorded, never derived); the generated config then carries a `CONTROL_DB` binding, `status` reports `[control]` and `[crm]` separately, and `upgrade` migrates control first, checks its tracker, then CRM, then deploys. - 946ccde: `vibase-server setup` names a new instance's resources `vb-<kind>-<env>` (Worker `vb-<env>`, D1 `vb-crm-<env>`, R2 `vb-bodies-<env>`, Workflow `vb-mail-sync-<env>`), refuses a name over 63 characters before any step, and never renames an existing instance: the names in the instance settings file win over the derivation, and a `--worker-name`, `--d1-name` or `--r2-name` that differs from the record is refused (exit 2).
- 53da87a: `vibase-server setup` creates, records and migrates the instance's control-plane D1 database `vb-control-<env>` (recorded as `control_d1` in the settings file; `--control-d1-name` overrides it, a name that differs from the record is refused with exit 2), migrates it before the CRM database, and writes the control marker after the CRM deployment row, including for an instance bootstrapped before.
