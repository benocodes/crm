# @vibase/server-d1

## 0.1.1

### Patch Changes

- 024d7a0: Invitations in the control plane. Control migration `0002` adds `invitations` and the append-only `control_audit` to the control database. Owners create, list and revoke invitations (`invitations.create|list|revoke`, owner-held human-only scopes `invitations:read|write`; the link is shown once and only its SHA-256 is stored). `bootstrap --auth-provider better-auth --owner-email <email>` issues the first owner invitation and prints its URL once; a re-run with no owner replaces it. The links are inert until invitation-gated sign-up lands.
- 7f02a06: Built-in auth clients and discovery. `bootstrap --auth-provider better-auth --public-base-url <origin>` seeds the first-party `vibase-cli` client into the control database (idempotent; no human is created). Open dynamic client registration is limited to public clients, the agent-grantable scopes and the API and MCP resources, 10 registrations per IP per hour. `/.well-known/vibase` carries `resource` on `better-auth`, the protected-resource documents and the RFC 8414 document at `/.well-known/oauth-authorization-server/auth` name `PUBLIC_BASE_URL`. `vibase login` finds a path issuer by RFC 8414 path insertion (appended form only on a non-200) and sends `resource` on device authorization, polling and refresh when discovery names one.
- 3076c7a: Invitation-gated sign-up on the built-in provider. `POST /auth/sign-up/email` creates an account only when its body carries `invitation_token` for a live invitation of that email; every other attempt is `403 invitation_required`. Signing up accepts the invitation: the vault writes the user (or, for an agent invitation, an agent account with no scopes) and the membership with their events, then the invitation is marked accepted with an `invitation.accepted` audit row. An account left without its vault rows is repaired on its next sign-in while the invitation that admitted it is still live. Invitation links from `bootstrap --owner-email` and `invitations.create` now work.
- 200c676: Membership writes and owner-issued reset links on the built-in provider. Owners (new owner-held, human-only scope `members:write`) change a member's role (`memberships.update`, `vibase memberships update <id> --role member`) or remove a member (`memberships.delete`, a soft delete): removing or demoting the last owner is `409 last_owner`, decided in the write's own statement. A removed member is denied at once (roles are read per request); the vault then revokes that person's sessions, OAuth access and refresh tokens and pending device codes and records a `user.sessions_revoked` audit row. `users.issue_reset_link` (`vibase users issue-reset-link --user-id <id>`) returns a one-time password reset link for a member, valid for one hour and shown once, with a `user.reset_link_issued` audit row; the public `POST /auth/request-password-reset` stays refused while email is off. On Clerk and on Postgres these operations answer `501 provider_not_configured`.
- 6f30ee5: Google sign-in on the built-in provider. With a complete Google client (`AUTH_GOOGLE_CLIENT_ID` and `AUTH_GOOGLE_CLIENT_SECRET`, else the Gmail client's `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`; half of the `AUTH_GOOGLE_*` pair fails closed naming the variable) `/sign-in` and `/invite` show a "Continue with Google" button, and `/.well-known/vibase`'s `better-auth` block gains `sign_in_methods` (`["password"]` or `["password","google"]`). Google signs in an existing account whose email Google reports verified and equal; a new account is created only through a live invitation for the Google-verified email (the token rides Better Auth's OAuth state, never a URL), else the callback returns to `/sign-in?error=invitation_required`. The vault user's `email_verified` follows the Better Auth user. The redirect URI to register on the Google client is `<PUBLIC_BASE_URL>/auth/callback/google`.
- cc2376c: CRM migration 0019 drops the dormant `auth_*` tables (they live in the control database now). The package ships `control-migrations/` under the new export `./control-migrations/*`, listed in `release.json` as `control_migrations`.
- f1aeec1: `vibase-server status` and `upgrade` handle an instance's control-plane database beside its CRM database. The instance settings take an optional `control_d1` (`name` and `id`, recorded, never derived); the generated config then carries a `CONTROL_DB` binding, `status` reports `[control]` and `[crm]` separately, and `upgrade` migrates control first, checks its tracker, then CRM, then deploys. Settings with `AUTH_PROVIDER=better-auth` and no `control_d1` are refused. Without `control_d1` both commands handle the CRM database only and print one not-configured line.
- 946ccde: `vibase-server setup` names a new instance's resources `vb-<kind>-<env>` (Worker `vb-<env>`, D1 `vb-crm-<env>`, R2 `vb-bodies-<env>`, Workflow `vb-mail-sync-<env>`), refuses a name over 63 characters before any step, and never renames an existing instance: the names in the instance settings file win over the derivation, and a `--worker-name`, `--d1-name` or `--r2-name` that differs from the record is refused (exit 2).
- 53da87a: `vibase-server setup` creates, records and migrates the instance's control-plane D1 database `vb-control-<env>` (recorded as `control_d1` in the settings file; `--control-d1-name` overrides it, a name that differs from the record is refused with exit 2), migrates it before the CRM database, and writes the control marker after the CRM deployment row, including for an instance bootstrapped before. An instance recorded without a control database gets one on its next run.
- 7b99d6f: The OpenAPI extension on tenant operations is now `x-vibase-proposal` (was `x-vault-proposal`), new executions default to a `@vibase.invalid` client reference, the local R2 bucket and Workflow are `vb-bodies` and `vb-mail-sync`, and the connect page's key variable is `VIBASE_API_KEY`.
- e821ff7: Auth pages on the built-in provider. The Worker serves `/sign-in`, `/invite` and `/reset-password` (one Preact bundle under `/ui/`, from the release's `assets/ui/`) with a strict content security policy, before the migration gate; on `clerk` and unset these paths are `404 not_found`. `/invite` turns the `/invite#token=` link into an account (the token is read from the fragment and removed from the address); `/sign-in` signs in and out and is the OAuth provider's login page (`loginPage` moved from `/auth/sign-in`); `/reset-password` sets a new password from a `/reset-password#token=` link, and a reset now ends every session of that user. The release's server package ships `assets/ui/` and its layout check requires it. `pnpm build` builds both assets.
- d6ae32b: OAuth pages on the built-in provider. The Worker also serves `/device` and `/consent` (the same bundle, headers and `better-auth`-only gate as the other auth pages; `run_worker_first` gains both paths). `vibase login` now ends in the browser: `verification_uri_complete` is `<PUBLIC_BASE_URL>/device?user_code=…`, where a signed-in person checks the code, sees the app and its scopes and approves or denies. An MCP client's authorization request resumes through `/sign-in` (the signed query is forwarded) and stops at `/consent` (`consentPage` is now `/consent`), where the person allows or denies all requested scopes. The device code format is pinned to 8 characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, 30 minutes, polled every 5 seconds; `/sign-in?return_to=` is honoured for `/device` and `/connect` only. The connect page is unchanged.
- c35739e: The `/connect` page works on `better-auth`: it signs the person in through the instance's own `/sign-in`, shows them and their agents (OAuth-delegated ones included), signs out, and is served under a `'self'`-only Content Security Policy with no third-party host. On `clerk` the page and policy are unchanged; two shared lines of copy no longer name Clerk.
